## Alcance autorizado de esta actividad

- Todos los cambios se realizan exclusivamente en `sdd/`.
- Se reutilizan los requisitos existentes con sus identificadores originales.
- La nueva sección Movilidad se incorpora por solicitud explícita posterior del usuario, con DEC-038–DEC-043 como fuente separada; no se inventa que ya existía en RF/HU originales ni se modifica la spec de reservas aprobada.
- La documentación original y el código se conservan sin modificaciones.
- No se ejecutan commits ni push.
- Cada especificación requiere aprobación explícita del usuario antes de crear **su** `plan.md` y **su** `tasks.md`.

Estas son instrucciones expresas del usuario para esta actividad, no requisitos nuevos del producto.

## Flujo de trabajo

1. **Consultar fuentes.** Identificar el requisito original y sus criterios de aceptación, reglas, calidad y restricciones. Usar las rutas reales inventariadas en `fuentes.md`.
2. **Delimitar la funcionalidad.** Seleccionar una entrada del índice de specs y mantener las prioridades P1/P2/P3 originales de sus historias. La numeración identifica documentos, no compromisos de entrega.
3. **Redactar el qué y el porqué.** Usar todas las secciones de la plantilla. Expresar criterios verificables en EARS, sin resolver stack, esquemas, algoritmos o contratos técnicos dentro de la spec. Las restricciones técnicas ya documentadas se consultan en la constitución.
4. **Aclarar.** Registrar cualquier vacío como `[NECESITA ACLARACIÓN: pregunta concreta]` y enlazarlo con `aclaraciones.md`. Preguntar **una cosa a la vez**, empezando por decisiones que cambian el comportamiento o bloquean la aceptación. Seguir entrevistas de hasta seis preguntas, como indica la skill; si quedan pendientes, conservarlos visibles y acordar otra ronda, sin resolverlos por suposición.
5. **Revisar y aprobar cada spec.** Presentar la versión concreta al usuario y solicitar aprobación explícita. Registrar respuesta, fecha y alcance en la propia spec. Un borrador, una propuesta o una respuesta a una aclaración no equivalen a aprobación de toda la spec.
6. **Planificar después de la aprobación.** Solo entonces crear `sdd/specs/NNN-funcionalidad/plan.md`: diseño técnico, dependencias, decisiones y verificaciones vinculadas a criterios aprobados. Resolver antes del plan las contradicciones o aclaraciones que lo bloqueen.
7. **Desglosar tareas.** Crear `tasks.md` para esa misma spec aprobada, con referencias a criterios y plan. No incorporar comportamientos sin fuente o aprobación.
8. **Analizar consistencia.** Comprobar cobertura, restricciones, dependencias entre specs y decisiones pendientes antes de implementar. La implementación requiere una actividad posterior que autorice cambios fuera de `sdd/`.
9. **Verificar y mantener trazabilidad.** Vincular la evidencia de aceptación a cada criterio cuando exista implementación. Un requisito mapeado no significa que esté aprobado, implementado o probado.

El flujo sigue «constitution → specify → clarify → plan → tasks → analyze → implement → converge» del README raíz, adaptando sus rutas a `sdd/`. No se ha inicializado GitHub Spec Kit ni se han generado `.specify/` o `specs/` en la raíz. La elección/configuración de herramientas no bloquea esta organización documental.

## Convenciones de trazabilidad

- Conservar `RF01`–`RF24`, `HU-01`–`HU-23`, `RN-01`–`RN-30`, `AC01`–`AC12`, `RC01`–`RC23`, `RS01`–`RS12`, `RP01`–`RP08`, `DA01`–`DA10` y `ADR-001`–`ADR-017` exactamente como aparecen en las fuentes.
- La skill usa criterios locales `RF-1`, `RF-2`, etc. Se mantienen **en un espacio de nombres distinto**: `001/RF-1` identifica el criterio local de la spec 001; no sustituye ni renumera `RF01`.
- Cada criterio local cita sus RF/HU/RN de origen o las DEC aprobadas que lo concretan. Se permite dividir un RF compuesto en varios criterios atómicos, conservando su referencia. Un cambio aprobado se distingue del texto original y no se le atribuye retrospectivamente.
- `F00`–`F18` son alias de documentos; `ACL-xx` identifica aclaraciones y `DEC-xxx` registra decisiones de entrevista. Son identificadores de gestión SDD, no reemplazan RF/HU/RN ni son ADR arquitectónicas.
- Los requisitos sin ID se citan por documento y sección; no se les asigna un RF oficial inventado.
- El español es el idioma de trabajo, coherente con las fuentes y con esta solicitud.

## Tratamiento de conflictos y propuestas

Una ADR aceptada sigue siendo una decisión documentada; un ejemplo de código o una propuesta no la reemplaza. Si dos fuentes discrepan, registrar ambas en `aclaraciones.md`, sin elegir silenciosamente una versión ni interpretar una omisión como derogación.

**PROPUESTA SDD:** estados de una spec: `Borrador` → `En aclaración` → `Pendiente de aprobación` → `Aprobada`. Los cambios de comportamiento posteriores requieren una nueva revisión y aprobación de la spec afectada. Esta convención organiza el trabajo y no altera el producto.

La división inicial en doce funcionalidades y el inicio por reservas son **PROPUESTAS SDD** fundamentadas en DA05/DA04. Movilidad se añade como 013 por solicitud expresa del usuario, no por un nuevo roadmap inferido. Cada spec necesita aprobación propia. Las modificaciones arquitectónicas se regirán por ADR existentes; esta actividad conserva cambios exclusivamente en `sdd/`.
